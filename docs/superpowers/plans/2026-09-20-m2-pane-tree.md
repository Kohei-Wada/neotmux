# M2 — Pane Tree Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Splits, focus, resize and close, driven entirely from Lua, with no pane-related key handling in the host.

**Architecture:** A binary split tree in `neotmux-core` over `PaneId`s, with no knowledge of PTYs or terminals. One function turns the tree and a rect into pane rects. The binary owns the map from `PaneId` to its PTY and `vt100` parser and asks core for the rects.

**Tech Stack:** `neotmux-core` (no dependencies), `portable-pty` 0.9, `vt100` 0.16.2, ratatui 0.30.

**Spec:** `docs/superpowers/specs/2026-09-19-neotmux-design.md` §6 (and §4.6 for the op buffer, §4.5 for drawing epochs, §2 for the crate graph)

## Global Constraints

- The layout model is a **binary** split tree. A leaf is a pane; an internal node has an orientation, exactly two children, and the fraction of its rect going to the first child. This is tmux's model and it has tmux's weakness — three equal columns stay equal only by accident — which is accepted (§1).
- **Rect assignment happens in exactly one function**, and no other code in the tree module computes geometry. That is what keeps "let Lua replace layout" a later option rather than a later restructuring.
- `neotmux-core` stays buildable and testable with **no terminal and no Lua**. The tree is a pure data structure over `PaneId`; it does not own PTYs. `neotmux-core/Cargo.toml` has zero dependencies today and must still have zero when this is done.
- `assign` is **total**: every cell of the window is covered by exactly one pane rect, no gaps, no overlap, at every size — including sizes too small to honour the fractions. Rounding error goes to the first child.
- No pane may be smaller than `neotmux_term::state::MIN_GRID` (2x2, measured against vt100 0.16.2 — below it vt100 panics). A split that cannot give both children that much is refused, not clamped into an empty rect.
- `split` and `focus` arrive as ops on the one op buffer and are applied after the tick (§4.6). A callback never sees its own request take effect.
- **There is no prefix and no pane keybinding in the host.** Every pane action is a plugin calling `neotmux.pane.*`. If something cannot be written that way, that is a finding to report, not a host feature to add.
- The host has no plugin concept. Identity is the chunk code was written in.
- Tests pin behaviour, not structure. No speculative abstraction.
- No `#[allow(...)]`. `cargo test --workspace`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` clean.

### Task 1: The tree, and one function that assigns rects

**Files:**
- Create: `crates/neotmux-core/src/layout.rs`
- Modify: `crates/neotmux-core/src/lib.rs`
- Test: in `crates/neotmux-core/src/layout.rs`

**Interfaces:**
- Produces: `Tree::new(PaneId)`, `Tree::split(&mut self, target: PaneId, dir: SplitDir, new: PaneId) -> Result<(), SplitRefused>`, `Tree::close(&mut self, pane: PaneId) -> Option<PaneId>` (the pane focus should move to), `Tree::panes(&self) -> Vec<PaneId>` in left-to-right, top-to-bottom order, and `layout::assign(&Tree, Rect) -> Vec<(PaneId, Rect)>`.

No PTYs, no `vt100`, no Lua. This task is pure data structure and is where the property test lives.

- [ ] **Step 1: Write the failing test — a single pane gets the whole rect**

```rust
#[test]
fn a_lone_pane_fills_the_surface() {
    let tree = Tree::new(PaneId::from(1));
    assert_eq!(
        assign(&tree, Rect::new(0, 0, 80, 24)),
        vec![(PaneId::from(1), Rect::new(0, 0, 80, 24))]
    );
}
```

- [ ] **Step 2: Run it and watch it fail** — `cargo test -p neotmux-core layout`, expected FAIL, `Tree` does not exist.
- [ ] **Step 3: Implement `Tree::new` and `assign` for the single-leaf case.**
- [ ] **Step 4: Run it and watch it pass.**
- [ ] **Step 5: Splitting — write the test, watch it fail, implement**

A vertical split of an 80x24 surface gives 40 and 40; a horizontal split gives 12 and 12. An odd size gives the extra cell to the first child (81 → 41 + 40) — assert that explicitly, because "rounding goes somewhere" is exactly the kind of thing that silently changes.

- [ ] **Step 6: Closing — write the test, watch it fail, implement**

Closing a pane replaces its parent with its sibling, and the sibling inherits the parent's rect. Assert that after closing one of two panes the survivor has the original whole rect back. Closing the only pane returns `None` and leaves the tree empty — the binary reads that as "exit".

- [ ] **Step 7: The property test**

```rust
#[test]
fn assigned_rects_tile_the_surface_exactly() {
    // For a set of tree shapes built by a deterministic sequence of splits, and every
    // surface from MIN_GRID up to 200x60: the rects are pairwise disjoint and their areas
    // sum to the surface area. No randomness — a fixed list of shapes, so a failure
    // reproduces.
}
```

Write it without a property-testing dependency: nested loops over a fixed list of split sequences and a fixed list of sizes. Adding a dev-dependency to `neotmux-core` for this is not worth it.

- [ ] **Step 8: Refusing a split that cannot fit**

A surface of 2x2 cannot be split: both children would be below `MIN_GRID`. `split` returns `Err(SplitRefused)` and the tree is unchanged. `neotmux-core` must not depend on `neotmux-term`, so the minimum is a parameter or a constant defined in core and re-exported — decide which, and say why in the commit message.

- [ ] **Step 9: Commit.**

### Task 2: One PTY per pane

**Files:**
- Modify: `crates/neotmux/src/panes.rs`, `crates/neotmux/src/app.rs`
- Test: `crates/neotmux/tests/fixtures.rs`

**Interfaces:**
- Consumes: Task 1's `Tree` and `assign`.
- Produces: `PaneLayout` backed by the tree; a `Panes` collection in the binary owning `PaneId -> (PtyHandle, TermState)`.

`PaneLayout::compute` in `crates/neotmux/src/panes.rs` is the single place that decides how many panes there are and what rect each gets — that was arranged in the M1a cleanup precisely so this task replaces one function.

- [ ] **Step 1: Write the failing test** — after a `split`, two PTYs exist and both children are alive.
- [ ] **Step 2: Run it and watch it fail.**
- [ ] **Step 3: Implement** — spawning a PTY on split, sizing each to its rect, resizing all of them when the surface changes.

- [ ] **Step 6: Input routing** — a key that no plugin consumes goes to the **focused** pane's PTY and no other. Test by writing to one pane and asserting the other's screen never changes.
- [ ] **Step 7: Commit.**

### Task 4: The prefix plugin, as a real fixture

**Files:**
- Modify: `crates/neotmux/tests/fixtures/lua/plugin/prefix.lua`, `crates/neotmux/tests/fixtures.rs`

`prefix.lua` already exists from M1a and proves `on_key` can build a two-key prefix that binds nothing. Extend it to do what a prefix is for: `C-a %` splits vertically, `C-a "` splits horizontally, `C-a o` focuses the next pane.

This is §6's third exit criterion and the honest test of the whole design: if the prefix needs anything the ABI does not offer, **report it and stop** — do not add a host feature to make it work.

- [ ] **Step 1: Write the failing test** over a PTY: send `C-a %`, assert two panes and that neither key reached a shell.
- [ ] **Step 2: Run it and watch it fail.**
- [ ] **Step 3: Write the plugin.**
- [ ] **Step 4: Run it and watch it pass.**
- [ ] **Step 5: Prove it is a plugin and not a feature** — delete the `require('plugin.prefix')` line and assert `C-a` reaches the shell as an ordinary keystroke, with the multiplexer otherwise working.
- [ ] **Step 6: Commit.**
